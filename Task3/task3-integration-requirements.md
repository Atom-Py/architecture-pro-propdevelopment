# Требования к внешним интеграциям сервисов «Умный дом»

Сервисы: интеллектуальный домофон (открытие по звонку, проход по лицу) и интеллектуальный шлагбаум (открытие из приложения, проезд по номеру автомобиля). Платформу и оборудование предоставляет партнёр, собственники работают с сервисами через текущее мобильное приложение.

Диаграммы: [task3-c4-context.drawio](task3-c4-context.drawio), [task3-c4-containers.drawio](task3-c4-containers.drawio).

## 1. Требования к безопасности

### Каналы связи и периметр

| № | Требование |
| :-: | :- |
| 1 | Весь обмен с платформой партнёра идёт через partner-gateway. Сервисы PropDevelopment не обращаются к партнёру напрямую, партнёр не обращается к внутренним сервисам |
| 2 | partner-gateway размещается в DMZ за межсетевым экраном, входящие соединения принимаются только с адресов партнёра из белого списка |
| 3 | Соединения с платформой партнёра защищены TLS 1.2 и выше (целевая версия TLS 1.3) с взаимной аутентификацией по сертификатам (mTLS), слабые наборы шифров отключены. Мобильное приложение подключается к сервисам PropDevelopment и платформе только по TLS |
| 4 | Видеопоток между мобильным приложением и платформой шифруется (WebRTC, DTLS-SRTP). Видео через системы PropDevelopment не проходит и не хранится |
| 5 | Шлюз проверяет каждый запрос и событие по контракту (OpenAPI, JSON Schema), ограничивает размер и частоту запросов для каждого партнёра, отклоняет неизвестные поля |

### Персональные и биометрические данные

| № | Требование |
| :-: | :- |
| 6 | Регистрация лица возможна только после письменного согласия на обработку биометрических ПДн (ст. 11 152-ФЗ). Согласие оформляется в приложении электронным документом с электронной подписью, отдельно для каждого человека, за ребёнка согласие даёт законный представитель |
| 7 | Фото и биометрические шаблоны в системах PropDevelopment не хранятся: приложение загружает фото напрямую в платформу партнёра по одноразовой ссылке. В smart-home-db хранятся только согласие и идентификатор записи у партнёра |
| 8 | Партнёру передаются псевдонимные идентификаторы жителей, номера автомобилей и привязка к дому, подъезду и парковке. Ф. И. О., телефоны, номера квартир и паспортные данные не передаются |
| 9 | Партнёр обрабатывает ПДн по поручению PropDevelopment (ч. 3 ст. 6 152-ФЗ), хранит их на территории РФ (ч. 5 ст. 18 152-ФЗ) и подтверждает соответствие обработки биометрии требованиям 572-ФЗ |
| 10 | При отзыве согласия, выезде жителя или смене собственника биометрия и номера автомобилей удаляются у партнёра в течение суток, партнёр подтверждает удаление |
| 11 | Сроки хранения закреплены в договоре: видео и снимки у партнёра не дольше 30 дней, журнал проходов в smart-home-db не дольше 1 года |
| 12 | smart-home-db не подключается к передаче сырых данных в хранилище по CDC. В хранилище уходит только обезличенная агрегированная статистика проходов |
| 13 | В журналах и событиях не записываются изображения и биометрия, номера автомобилей маскируются |

### Авторизация и изоляция данных

| № | Требование |
| :-: | :- |
| 14 | smart-home-app при каждом запросе проверяет, что пользователь из токена имеет право на квартиру, дом, подъезд или парковку, к которым относится действие. Права вычисляются по данным CRM о собственности, идентификаторам из запроса без проверки сервис не доверяет |
| 15 | Добавлять жителей и номера автомобилей может только собственник квартиры, члены семьи управляют только своими данными |
| 16 | Удалённое открытие двери и шлагбаума, добавление жителя и номера автомобиля, регистрация лица требуют повторного подтверждения в приложении: биометрия телефона или PIN-код |
| 17 | Данные PropDevelopment на платформе изолированы от других клиентов партнёра. Токены PropDevelopment дают доступ только к её объектам, шлюз отклоняет события по объектам, которых нет в реестре объектов smart-home-app |
| 18 | Команда открытия действует не дольше 10 секунд и передаётся с ключом идемпотентности, просроченная или повторная команда отклоняется |
| 19 | Распознавание лиц выполняется с проверкой живого присутствия (liveness), которая защищает от фото, видео и масок. Допустимая доля ложных допусков фиксируется в договоре и проверяется при приёмке |
| 20 | При смене собственника по данным CRM все доступы квартиры отзываются в течение 15 минут, в том числе на платформе партнёра |

### Ключи, устройства и контроль

| № | Требование |
| :-: | :- |
| 21 | Ключи, сертификаты и учётные данные хранятся в хранилище секретов и не попадают в код, образы и конфигурацию. Сертификаты и ключи подписи ротируются не реже раза в год и сразу при компрометации |
| 22 | У каждого устройства на объекте свой сертификат, прошивки подписаны производителем, заводские пароли отключены, обновления устанавливаются централизованно |
| 23 | Каждая команда и событие записываются в журнал smart-home-app: кто, когда, какой объект, способ открытия (лицо, номер, вызов, приложение), результат. Журналы безопасности шлюза и smart-home-app передаются в систему централизованного мониторинга |
| 24 | Настроены оповещения о серии неудачных распознаваний, массовых командах открытия, событиях по неизвестным объектам, ошибках проверки подписи и сертификатов |
| 25 | Партнёр проходит оценку ИБ до подключения и затем ежегодно: тест на проникновение API и платформы, отчёт о мерах защиты ПДн. Об инцидентах с данными PropDevelopment партнёр сообщает не позднее 12 часов, чтобы компания уведомила Роскомнадзор в срок 24 часа |
| 26 | Контракты API и их изменения согласуются со специалистом по ИБ, интеграция вносится в реестр внешних интеграций |

## 2. Протоколы аутентификации и авторизации

| Взаимодействие | Аутентификация | Авторизация |
| :- | :- | :- |
| Собственник, мобильное приложение и auth-service-1 | OpenID Connect, Authorization Code с PKCE. Собственники ведутся в отдельном realm Keycloak, не пересекающемся с покупателями. Access token (JWT) живёт 5 минут, refresh token ротируется при каждом использовании. Повторное подтверждение для чувствительных действий запрашивается через acr (step-up) | Роли «собственник» и «член семьи», scopes `smart-home.read`, `smart-home.manage`, `smart-home.open` |
| Мобильное приложение и smart-home-app | OAuth 2.0 Bearer, проверка подписи JWT по JWKS auth-service-1, проверка `iss`, `aud`, `exp` | Scopes из токена и проверка по атрибутам: квартира, дом, подъезд, парковка по данным CRM (требование 14) |
| smart-home-app и partner-gateway | mTLS между сервисами внутри контура | Шлюз пропускает от smart-home-app только маршруты платформы «Умный дом» и push-сервисов |
| partner-gateway и платформа партнёра | OAuth 2.0 Client Credentials с аутентификацией клиента по сертификату (mTLS, RFC 8705). Токен привязан к сертификату и живёт не дольше 15 минут | Scopes на функции: `access-lists.write`, `commands.open`, `video-sessions.create`, `enrollment.create`. Область действия ограничена объектами PropDevelopment |
| Платформа партнёра и partner-gateway (события) | mTLS с закреплённым сертификатом партнёра. Каждое событие подписано JWS ключом партнёра, шлюз проверяет подпись, время события (окно 5 минут) и уникальность идентификатора | Принимаются только типы событий из контракта и только по объектам из реестра |
| Мобильное приложение и платформа партнёра (видео, фото) | Одноразовый токен видеосессии или ссылка загрузки фото, которые партнёр выпускает по запросу smart-home-app. Токен видеосессии живёт 60 секунд, ссылка загрузки 5 минут | Токен привязан к пользователю и к конкретному вызову или записи о регистрации лица |
| partner-gateway и сервисы push-уведомлений | Ключ APNs и сервисный аккаунт FCM из хранилища секретов | В уведомлении только тип события и идентификатор вызова, без Ф. И. О. и изображения |
| Устройства и платформа партнёра | X.509-сертификат устройства, mTLS | Устройство передаёт события и принимает команды только по своему объекту |

## 3. Организация взаимодействия

### Компоненты

| Компонент | Назначение |
| :- | :- |
| Витрина сервисов для собственников | Новый раздел «Умный дом»: жители, номера автомобилей, согласия, журнал проходов, ответ на вызов, открытие двери и шлагбаума |
| smart-home-app | Права доступа в дома и на парковки, реестр объектов и устройств, согласия, журнал событий, команды открытия, выдача токенов видеосессий |
| smart-home-db | Права доступа, номера автомобилей, согласия, идентификаторы записей у партнёра, журнал событий |
| partner-gateway | Единая точка обмена с внешними платформами: mTLS, OAuth 2.0, проверка контрактов, лимиты, журнал вызовов. Через него же в дальнейшем подключаются существующие интеграции с управляющими компаниями |
| CRM | Источник данных о собственниках и квартирах |
| Хранилище данных | Получает обезличенную статистику проходов |
| Платформа «Умный дом» партнёра | Видеозвонки, распознавание лиц и номеров, решения о проходе, управление устройствами |

### Принципы обмена

1. Источник прав доступа - PropDevelopment: smart-home-app по данным CRM решает, кто и куда может проходить. Платформа хранит копию списков доступа и принимает решение у устройства, поэтому проход по лицу и проезд по номеру работают без обращения к PropDevelopment.
2. Синхронно, REST через шлюз: команды открытия, изменение списков доступа, запрос видеосессии и ссылки загрузки фото. Таймаут 3 секунды, повторяются только идемпотентные запросы, при серии ошибок шлюз размыкает цепь (circuit breaker).
3. Асинхронно, webhook от платформы: вызов домофона, проход, проезд, результат регистрации лица, состояние устройства. Доставка «хотя бы один раз», партнёр повторяет отправку с нарастающей задержкой, smart-home-app отбрасывает дубли по идентификатору события.
4. Изменения списков доступа передаются партнёру сразу, раз в сутки выполняется полная сверка smart-home-db с платформой, расхождения исправляются и записываются в журнал.
5. smart-home-app запрашивает в CRM изменения собственности каждые 5 минут и раз в сутки выполняет полную сверку.
6. Контракты описываются в OpenAPI для REST и AsyncAPI для событий, версия указывается в пути (`/v1`), несовместимые изменения выпускаются только новой версией.

### Сценарии

| Сценарий | Взаимодействие |
| :- | :- |
| Добавление жителя или номера автомобиля | 1. Собственник добавляет жителя или номер в приложении и подтверждает действие биометрией телефона или PIN-кодом. 2. smart-home-app проверяет по CRM, что пользователь собственник этой квартиры, и сохраняет запись. 3. Через шлюз обновляет список доступа на платформе. 4. Приложение показывает статус синхронизации |
| Регистрация лица | 1. Житель подписывает согласие на обработку биометрии в приложении. 2. smart-home-app сохраняет согласие и через шлюз запрашивает у платформы одноразовую ссылку загрузки. 3. Приложение загружает фото напрямую в платформу. 4. Платформа присылает событие о результате регистрации, smart-home-app сохраняет идентификатор записи |
| Проход по лицу или проезд по номеру | 1. Устройство передаёт кадр на платформу. 2. Платформа распознаёт лицо или номер и проверяет его по копии списка доступа. 3. Открывает дверь или шлагбаум. 4. Отправляет событие в шлюз, smart-home-app записывает его в журнал |
| Вызов домофона и открытие по звонку | 1. Посетитель звонит в квартиру. 2. Платформа отправляет событие вызова в шлюз. 3. smart-home-app находит жителей квартиры и через шлюз отправляет push-уведомление. 4. Приложение получает у smart-home-app одноразовый токен и подключается к видеопотоку платформы. 5. Житель нажимает «Открыть», smart-home-app отправляет команду открытия через шлюз |
| Открытие шлагбаума из приложения | 1. Житель выбирает шлагбаум своей парковки и подтверждает действие. 2. smart-home-app проверяет право на парковку и отправляет команду через шлюз. 3. Платформа присылает событие об открытии |
| Смена собственника или отзыв согласия | 1. smart-home-app получает изменение из CRM или отзыв согласия из приложения. 2. Отключает доступы в smart-home-db и через шлюз удаляет записи на платформе. 3. Платформа подтверждает удаление событием, подтверждение сохраняется в журнале |

### Отказы и уровень сервиса

| Ситуация | Поведение |
| :- | :- |
| Платформа партнёра недоступна | Приложение сообщает, что сервис временно недоступен. Команды открытия не ставятся в очередь, чтобы устаревшая команда не открыла дверь позже. Устройства на объекте продолжают работать по локальным спискам и ключам |
| Системы PropDevelopment недоступны | Устройства работают по последней синхронизированной копии списков доступа, события копятся у партнёра не менее 24 часов и доставляются после восстановления |
| Уровень сервиса партнёра | Доступность API 99,9%, решение о проходе по лицу или номеру не дольше 1 секунды, доставка события вызова не дольше 2 секунд |
